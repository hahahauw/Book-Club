# Quality-of-life audit and repairs — 12 September 2026

Baseline: `dbb28d2a6a827a2ffd9dc9da776ad76f0ef3bee3` on main, including merged PR #15.

This is a repository-based follow-up audit of functionality, recovery paths, accessibility, and maintainability. Security rules and production data were not tested or changed. No live account actions or rendered device tests were performed. “Confirmed” below means the failure path exists in the source, not that it was reproduced against a member's production account.

## Outcome

The immediate need is more reliable transitions between existing features, rather than another visual redesign. Five related problem groups were identified and repaired in this change. The cover layout, theme styles, database schema, and Firestore rules are unchanged. The application asset version advances from 26 to 27.

| ID | Priority | Confidence | Problem | Repair |
| --- | --- | --- | --- | --- |
| QOL-01 | P1 | Confirmed | Unavailable browser storage can stop application startup or interrupt theme/filter actions. | Guard preference reads/writes and retain failed writes in memory for this visit. |
| QOL-02 | P2 | Confirmed | Catalogue selection and save state can disagree with the user's current action. | Clear obsolete selection/results, guard submissions, lock fields during saving, invalidate closed-dialog requests, remove delayed closure. |
| QOL-03 | P2 | Confirmed | A single global dialog opener loses the correct focus destination in nested dialogs. | Keep a separate opener for each dialog and handle native close events, including Escape. |
| QOL-04 | P2 | Confirmed | Manual catalogue entry can end at instructions instead of an input form. | Open the user's library, expand its form, preserve the selected reading status, and focus the title field. |
| QOL-05 | P1 | Confirmed | Loading or failed member profiles have no on-screen Close button. | Keep an explicitly labelled close control during loading and failure. |

Priority describes the pre-repair impact. P1: major failure or accessibility barrier; P2: meaningful state or usability bug. These are five groups, not five separate claims of deployed failures.

## Findings and reproduction paths

### QOL-01: Preferences must not be required for the app to run

Location: state initialization, `setTheme`, `renderBooks`, `toggleShelfLayout`, integration-settings save, and shelf filter handlers in `app.js`.

Previously, storage getters and setters were accessed directly. A browser that throws on access stops state initialization before application listeners are established. A full storage quota can also throw during a theme or filter action. Theme changes could partially apply before labels updated; shelf expansion could be lost on the next render.

Trigger: simulate a throwing localStorage/sessionStorage getter, or a quota error on setItem. Expected: use defaults and keep the current visit interactive. The repair makes persistence best-effort and preserves same-visit choices after a failed write. Successful writes still allow later reads to see changes from another tab. Preferences cannot survive a reload if the browser refuses persistence; Firebase sign-in storage behavior is separate and was not evaluated here.

Effort: Small. Dependencies: none.

### QOL-02: Catalogue operations need one coherent selection

Location: `openCatalog`, `submitCatalogSearch`, `selectCatalogBook`, `saveCatalogBook`, and the catalogue close listener.

Previously, choosing B while details for B loaded left A's preview and saveable state in place. Starting a new search left previous result buttons active. Saving disabled only the save button: fields and destination could still change while helper functions awaited database reads, then used those fields. There was no direct repeated-call guard. After success, a 900ms timer could close a newly reopened catalogue.

Triggers: select A, then B on a slow connection; start a new search and click an old result; change destination while saving; close and reopen immediately after a successful save. Expected: selection, preview, and saved data agree, and an old operation cannot close the next session.

The repair hides and clears an obsolete selection immediately, removes previous search results during a new search, retains latest-request guards, locks catalogue controls while saving, rejects repeated saves, prevents reopening during an outstanding save, and closes successful saves immediately. Existing success toasts remain. Close remains available. Empty guest names are checked before controls are locked. Closed-dialog searches and detail requests are invalidated rather than allowed to update the next view.

Effort: Medium. Dependencies: dialog closing behavior in QOL-03 is exercised alongside this flow. This is not a claim that all cross-tab recommendation duplication is resolved.

### QOL-03: Nested dialogs need independent focus restoration

Location: `showDialog`, `closeDialog`, new `restoreDialogFocus`, and the Memories viewer.

Previously, opening a book from a library overwrote the library's original opener. Closing the book cleared that shared value, so closing the library could no longer restore it. The custom path did not cover native Escape consistently. Route changes into Memories also attempted to focus the background heading while its photo dialog was opening.

Trigger: keyboard-open My library, open a book, close the book, then close the library; repeat with Escape. Expected: focus returns to the relevant opener at each level. Each dialog now retains its own opener and restores it from the native close event. Queued focus callbacks check the active dialog, and a transition does not steal focus from a newly opened dialog. Missing photo openers fall back to the gallery heading when available.

Effort: Medium. Dependencies: real browser keyboard and Android Back behavior still need device verification; mock close-event tests cannot certify browser focus handling.

### QOL-04: Manual entry should be a working fallback

Location: `openManualCatalogEntry`.

Previously, selecting a personal shelf destination then choosing manual entry only worked when a shelf form happened to exist. Otherwise the catalogue closed and a toast told the user to navigate elsewhere. An existing but closed profile could also contain a form the user could not reach. The expansion toggle and selected shelf were not kept in sync.

Trigger: open the catalogue from the general shelf, choose Want to read, then choose manual entry. Expected: land in the user's visible add-book form with Want to read selected. The repair opens or reuses the correct library, checks that it is still the current destination after loading, expands the form, updates aria-expanded, and focuses its title field. A failed profile load gives a recoverable message.

Effort: Small. Dependencies: QOL-03 and QOL-05 support this transition.

### QOL-05: Failed profiles must remain dismissible on touch screens

Location: `openProfile` loading and catch branches.

Previously, the close control existed only in the successful profile markup. During a slow or failed read, the dialog instead contained a skeleton or an error paragraph. Desktop Escape could work, but a phone user had no visible close action.

Trigger: open a missing profile or delay/fail its read. Expected: a visible labelled Close button remains available throughout loading, success, and failure. Both non-success views now include it; the error is also a status message.

Effort: Small. Dependencies: none.

## Practical roadmap

1. Review and apply the five repairs above after smoke testing the branch.
2. On the actual phone and a desktop browser, test theme switching, saved status, profile failure dismissal, and nested dialog focus. Capture image-network evidence if pinboard initials persist.
3. Add reproducible browser fixtures for guest, member, officer, empty, slow-loading, and failed-loading states. Existing tests mostly exercise isolated functions or source structure; they are not a substitute for screenshots or browser interaction.
4. Consider older-discussion pagination and gallery search once members accumulate enough content to need them.
5. Consolidate CSS gradually with those browser fixtures. Keep the current vanilla JavaScript architecture unless a concrete change makes a module boundary useful.

Not worth doing now: a framework migration, a complete redesign, a new recommendation engine, or enterprise-scale infrastructure. They would add migration risk without solving the reported club workflows.

## Validation

67 targeted tests passed across the new quality-of-life tests and the existing visual-source, library, catalogue, Memories, event, and discussion regression suites. JavaScript syntax and whitespace checks passed. The new tests cover denied storage, quota failure, stale detail responses, clearing old results, duplicate save attempts, failure unlock, immediate successful closure, manual entry, profile close controls, and nested close events. The existing Memories fixture was updated to supply the new per-dialog opener map.

No rendered browser or real-device pass was performed. This report therefore does not certify contrast, mobile layout, screen-reader behavior, Android Back semantics, or production network resilience. No security tests were run and no production data was written.
